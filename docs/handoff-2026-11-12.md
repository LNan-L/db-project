## 五、环境坑（踩过的，别再踩）

1. **本机没有系统级 Node**：必须先加便携 Node 路径才能用 `npm`。
2. **GitHub 直连不可用**：用 `https://gh-proxy.com/<github-url>` 镜像。
3. **Tailscale Funnel 在大陆网络不稳**；只用 tailnet 的 `serve`。
4. **PWA 需要安全上下文**：`http://100.x` 不能安装/离线；`https://*.ts.net` 正常。
5. **换 origin = 本地数据看不见**（数据还在旧 origin）；切入口前先同步一次。
6. **内联 base64 会撑爆正文**：正文用 `![name](attachment:<id>)`，编辑器显示时换 data URL。
7. **游标自愈**：本地 0 篇 + 有游标时强制全量拉。
8. **`server/*.js` 是 CommonJS**（根 `package.json` 是 ESM），作用域由 `server/package.json` 隔离。
9. **PC 同步走 tailnet**：地址用 ts.net，不要写成 `http://10.0.0.10:3000`（服务只监听回环）。
10. **画布布局是本机数据**：`canvas_cards`（schema v6）不同步、不进备份。
11. **不要用浏览器原生 `window.confirm` 做关键操作确认**：会被拦或不可见，表现为「点了没反应」。
    Phase 5.0.1 已把 AI 授权/重建确认改成面板内联确认；新写确认一律用内联行。
12. **AI 面板「保存」不再要求远端授权**：授权只影响使用；遇到「测试连接失败」先看有没有填 key。

### 2. 卡点根因与修复（E2E 读源码的问题）

- 现象：该 spec 早期版本直接 import `src/backup/crypto.ts`，而 E2E 跑的是 production build
  （`vite preview`），不提供 `/src`，测试拿不到加密实现。接手时文件已按「Node 侧自加密」改了一半。
- 采取的方向（已落地）：测试不再 import 应用源码，**在 Node 侧按同一二进制格式自己加密**
  （`PKEB1 | version | saltP | ivP | wrappedDEK(P) | saltR | ivR | wrappedDEK(R) | ivData | ciphertext`），
  用 `crypto.subtle` 生成真实 `.pke.enc` 写到 `os.tmpdir()`，再通过 `setInputFiles` 交给页面。
- 真正让 Playwright 起不来的不是 `/src`，而是半成品用了 `node:crypto` 的 `webcrypto`：它的
  `webcrypto.CryptoKey` 与 DOM 的 `CryptoKey` 不兼容（`KeyUsage` 含 `decapsulateBits`），
  `tsc --noEmit` 报 TS2322，`npm run build` 失败。改为直接用全局 `crypto`（Node 22 已内置 WebCrypto）
  后类型统一，构建恢复。**注意：webServer 是 `npm run build && npm run preview`，
  任何 TS 报错都会表现为「webServer 无法启动」，不要误判成端口/配置问题。**
- 三条 E2E：正常换口令、错误旧口令被拒、新口令不足 12 位被拒。
- **第 4 条 E2E 是往返验证**（`a rekeyed backup imports under the new passphrase`）：fixture 用
  `fflate` 造一个合法 schema v2 包（manifest + 带 frontmatter 的 Markdown，hash 为正文 UTF-8 字节的
  SHA-256），换口令后把**下载到的新包**在全新 browser context 里用新口令导入，断言 `新增 1`、
  `note-count=1`、笔记标题出现。这补上了「只断言提示文案」的盲区——旧包能换、换完不能导入的问题现在会红。
  旧口令打不开新包由单测 `re-wraps the same payload under a new passphrase` 覆盖。

### 6. 手机验收发现的同步幂等问题（2026-11-13 01:14 修复并部署）

手机真机验收第一轮就暴露了两个写入放大问题：

1. **一次编辑涨两个 revision**：实验2 从 5 → 6 → 7，版本历史多一条。
   根因：客户端用 `note.updatedAt`（手机时钟）比 `lastSyncAt`（服务端时间），
   手机快约 1.1s → 刚推完的笔记看起来"仍然更新"，下一轮又推一次。
2. **附件元数据每轮重同步**：每次同步都显示「附件 0/1」，服务端附件行 `synced_at`
   被反复刷、`name` 密文每次变化。根因：开 key 后同一明文每次 IV 不同，
   而幂等判断比较的是**密文**，永远不相等。

### 8. 手机 PWA 附件按钮点不动（2026-11-13 16:13 修复并部署）

现象：手机上从主屏幕图标（PWA 独立窗口）打开，点「添加附件」完全没反应。

根因：触发点是 `<label>` 包一个 `display:none` 的 `<input type="file">`，靠隐式激活打开选择器。
Android 的 standalone 模式/部分 WebView 不认这种写法，也不会为不可渲染的 input 打开选择器。

修复：改成真实 `<button data-testid="attachment-add">` 调 `input.click()`；input 保留在渲染树里，
用 `clip-path` 视觉隐藏而不是 `display:none`（`.attachment-input-hidden`）。

回归：`tests/e2e/attachments.spec.ts` 新增 390px 用例，断言点按钮真的触发 `filechooser`，
